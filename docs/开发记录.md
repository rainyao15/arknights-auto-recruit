### 不再弹黑框（2026-11-03 修）

打包成 windowed exe 后，**每一次 adb 调用都会弹一个黑色控制台窗口再消失**
（一顿招募几十上百次调用，看起来就是"窗口一直弹"）。已在 `core/adb_client.py`
给所有 `subprocess.run` 加：

```python
creationflags = 0x08000000   # CREATE_NO_WINDOW
startupinfo.dwFlags |= STARTF_USESHOWWINDOW
startupinfo.wShowWindow = 0  # SW_HIDE
```

效果：全程零黑框、不抢焦点，面板最小化也不会打扰你正常用电脑。

### 时长直接就位（不是一小时一小时等）

游戏里**没有**"直接 9 小时"的入口，招募时限上限就是 `09:00:00`（点过头会绕回 01:00），
所以只能点「+」。优化到极限的做法：

1. 先读一次当前时长（FastOcr 60ms）；
2. 算出还差几格，**一条 adb 命令连点**（`input tap` 串联，8 下 ≈0.5s，实测 20ms 间隔 100% 命中）；
3. `need == 0` 时一下都不点（防止 9:00 被点回 1:00）；
4. 每轮只校验一次（60ms），点漏了就地补；之后三格直接跳过校验。

### 弹窗（一直弹的那个已治）

根因不是"弹窗多"，是**联络次数 0/3 时还在点卡片**，游戏就一直弹
`是否消耗1次联络机会？`。现在的处理：

| 场景 | 处理 |
|------|------|
| 任何弹窗 | `kill_popups_fast()` 用 60ms 的 rec 认出 `是否/确定/取消/不足/上限` → 点 ✗ |
| 挂单没提交成功 | 清弹窗 → 记为失败；**连续 3 格失败**才收工 |
| 招募预算 0/1 | 面板上读到「招募预算 0/1」→ 直接收工并通知 |
| 收工 | 先把面板/弹窗清干净再退出，游戏留在列表页 |

⚠️ **勘误（2026-11-03 晚）**：之前把「联络次数 0/3」当成"今天不能招募了"是**错的**。
联络次数指的是人脉联络/刷新标签的额度，和能不能开公招位**无关**。
实测：联络次数一直 0/3，照样连开 4 个位，招募预算从 839 → 835。
真正的限制是面板上的「招募预算 N/1」，所以现在只在 `N == 0` 时停。

### 极速路径（2026-11-03 晚重构）

瓶颈不是点击，是 OCR + 截图：

| 动作 | 耗时 |
|------|------|
| 全屏 RapidOCR | 4000~6000 ms |
| 裁区域 + 检测 | 1000~1500 ms |
| **FastOcr（只识别不检测，固定小裁块）** | **50~70 ms** |
| `exec-out screencap`（raw） | 660 ms（PNG 774 ms） |

所以改成：**一帧多次复用 + 只在小裁块上做 rec**。真机实测：

| 阶段 | 改前 | 改后 |
|------|------|------|
| 挂单（读词条→选词条→9h→开始招募） | 30~60s | **2~4s** |
| 领取（加急→聘用→SKIP→读出货） | 20~30s | **3.5~4s** |
| 一轮四格 | 4~5 分钟 | **约 25~30 秒** |

坐标全在 `config.ui.fast`（time / header / list_head / name / tag_grid / cards），
按 1600x900 标定；分辨率不符时 `UI.fast_ready()` 会自动退回慢速全屏 OCR。

## 核心原理（为什么这么决策）

公招的底层规则（来自官方拆包数据 `gacha_table.json`）：

- **只有 2 个词条影响星级**：
  - `高级资深干员` → 必得 **6★**
  - `资深干员` → 必得 **5★**
- 其余 29 个词条只决定"同星级内抽到谁"，**不改变星级**。
- 因此当你**不看人物价值、干员全解锁、纯刷黄绿票**时，同星级干员收益相同，决策退化成三条规则：

```
有「高级资深干员」→ 单独选它                       → 6★
否则有「资深干员」 → 单独选它                       → 5★
否则 → 枚举 1~3 个词条的组合，找「池内最低星最高」的：
        召唤        → 池里只剩 豆苗(4★)            → 保底 4★   ← 必须点
        输出+群攻   → 池里只剩 4★                  → 保底 4★
        只有降星词条（新手/元素/支援机械）→ 一个都不选 → 3★~4★ 随机
```

⚠️ 初版写的是「任选一个词条」，这是**错的**：普通词条只收窄池子，不提升星级；
但当某个词条（或组合）的池子里**最弱的干员都 ≥4★** 时，选它就是把「3★~4★ 随机」
变成「保底 4★」。`召唤` 就是最典型的例子（池：豆苗 4★ / 梅尔 5★ / 凯尔希 6★，
没选资深时 5★/6★ 进不了池，所以只剩豆苗 → 百分百 4★）。现在由
`decision.guarantee_best()` 自动枚举组合找这种保底，找到了就点。

这就是"刷黄绿票"目标下的数学最优，比 MAA 的决策简单一个数量级（MAA 复杂是因为要帮普通玩家锁特定干员）。

数据来源：[MAA 的 recruitment.json](https://github.com/MaaAssistantArknights/MaaAssistantArknights)（官方拆包生成，随版本更新），已缓存到 `data/recruitment.json`。

## 一个 exe 搞定（免 Python、免一堆 bat）

**只需要一个文件：`dist/明日方舟公招面板/明日方舟公招面板.exe`。**
以前那四个 bat（启动 / 管理员启动 / CLI 跑一轮 / 打包）全部合并进 exe 里了：

| 以前 | 现在 |
|---|---|
| `启动面板.bat` | 双击 exe |
| `启动面板-管理员.bat` | exe **自己判断**要不要管理员，需要就弹一次 UAC 把自己重启成管理员 |
| `pc_run_管理员.bat --once` | 面板左侧把「轮数」填 `1` 再打开开关（等价） |
| `打包exe.bat` | 只有改代码后重打包才用（日常不用管） |

自动提权的判定逻辑（`core/elevation.py`）：

```
启动 → 是管理员吗？ ── 是 ──→ 直接进面板
                │
                └ 否 → 这次用 ADB 还是 PC？
                        ├ ADB（模拟器）→ 不用提权，直接进面板
                        └ PC 且游戏进程受保护（OpenProcess 被拒）
                              → ShellExecuteW("runas") 自我重启 → UAC → 面板
```

嫌烦可以 `明日方舟公招面板.exe --no-elevate` 关掉自动提权；面板左下角也会显示
「权限：普通用户 [以管理员重启]」，随时补一刀。点「开始」时如果不满足条件，还会再问一次。

**首次启动自给自足**：exe 里内置了一份默认 `config.yaml` 和词条数据，第一次跑会自动在
exe 旁边生成，之后你改的就是那一份（内置的那份不会再覆盖）。

```
dist/明日方舟公招面板/
├── 明日方舟公招面板.exe      ← 只有这个是你需要点的
├── config.yaml               ← 首次启动自动生成，随时改
├── data/recruitment.json     ← 首次启动自动生成（离线可用）
├── logs/                     ← 运行日志 + history.jsonl（自动生成）
└── _internal/                ← Python 运行时 / onnxruntime / OCR 模型（别动）
```

重新打包：

```bash
打包exe.bat        # 装 PyInstaller → 打包 → 自动备份/恢复你改过的 config.yaml
```

为什么是 onedir 不是 onefile：OCR 模型 + onnxruntime 有 260MB+，onefile 每次启动都要解压到临时目录，
冷启动 8~15 秒；onedir 直接跑，实测 **0.5 秒**出窗口（PE subsystem = Windows GUI，无黑框）。

打包后自检（写文件后退出，适合无控制台验证）：

```bash

dist\明日方舟公招面板\明日方舟公招面板.exe --check-ocr    # → logs/ocr_check.txt: OK 公开招募 | 高级资深干员 | 09:00
```

## 为什么「领完一个后一直对着空气点、过一会才招第二个」（2026-11-07 修）

截图定位到真相：这个号的**3、4 号位是锁着的**（`人力办公室2级后解锁` / `3级后解锁`），
只有 1、2 号位能用。而脚本按 `max_slots: 4` 每轮都去点 3、4 号位：

```
点 3 号位 → 没反应（锁着的）→ 补点一次 → 还是没反应
        → 判定「other」→ 掉进慢速全屏 OCR（4~6s）→ 再 cancel_panel 收尾
        → 4 号位再来一遍（又是 5~10s）
```

这就是你看到的「对着空气点三四下、过一会才招下一个」。

现在改成**记住没解锁的格子，整局不再碰**：

| 位置 | 改动 |
|---|---|
| `runner.place_slot()` | 补点之后 `panel_state` 还是 `other` 且仍在列表页 → 判定未解锁，记进 `ui.locked_slots`，直接返回（不再进慢速 OCR） |
| `runner.run_cycle()` | 每轮开头先把 `locked_slots` 从槽位里剔掉；全被剔掉就本轮跳过 |
| 面板 | 状态栏显示「跳过未解锁槽位 [3, 4]」 |

判定有两条路，双保险：

1. **启动时读一次列表页**：`ui.detect_locked_slots()` 认卡片上的「…后解锁」文字，
   按坐标归到最近的槽位（不依赖文案/语言/布局），命中就在日志里报「检测到 3、4 号位未解锁」，
   并且**把面板上的勾选框自动取消**，你一眼就知道为什么只跑 2 格。
2. **点击反馈兜底**：万一图文识别漏了，补点后仍打不开面板且还在列表页 → 同样判定未解锁，整局不再碰。

> 为什么「我选的是单个招募栏一直招募」还会点到 3、4 号位？
> 面板上「打法」和「槽位」是两个独立选项：
> - **标准（一槽到底）** 说的是**节奏**（挂一个立刻领一个），不是**数量**；
> - 真正决定跑哪几格的是左侧「公招位 1 2 3 4」的勾选，默认**全勾**。
>
> 所以以前就算选了标准模式，脚本照样会去点 3、4 号位。现在启动时识别到没解锁会自动取消勾选，
> 想固定只跑某几格也可以手动取消。顺带修了个静默 bug：**一个都不勾时，`run()` 以前会偷偷改回 1~4 号位**，
> 现在直接报错不启动。

单测：`test_locked_slots_are_skipped`（锁 3/4 后，挂单事件里只允许 1、2）。

## 为什么「回到大厅还要空点好几下」（2026-11-07 修）

领完干员回到公招列表，脚本还会对着屏幕中央再点 2~3 下，全打在空地上。
根因是**点完不等结果**：

```
点左下空白关卡 → 固定 sleep(0.2s) → 转场动画还没结束
              → screen_kind() 读到 other（既不是卡也不是列表）
              → 判定「还没到列表」，再点一次中央
              → 此时已经是列表页，这一下纯空点
```

修法：新增 `_wait_change(before)` —— 点完之后等**帧差 > 1.5** 才算界面有反应，
最多等 `ui.ui_settle`（0.9s）；**没反应就立刻收手**，绝不补刀。

```yaml
ui:
  ui_settle: 0.9   # 点完后等界面变化的上限；没变化 = 空点，停止
```

改动点：

| 位置 | 行为 |
|---|---|
| `skip_result_pages()` | 每下之后等变化；没变化 → 立即 return，不再连点 |
| `close_result()`（慢速路径） | 中央补点后等变化，没变化直接 break |
| `ensure_list_fast()` | 「轻点中央推进」原来死等 1.2s，现在一有变化就继续 |

效果：正常情况 **1 下关卡 + 1 下快进介绍页** 就回列表；界面不动时最多 1 下就收手
（有单测兜着：`test_skip_result_pages_no_blind_retap`）。

## 为什么「领完一个就开始发呆」（2026-11-07 修）

实测日志（19:07）暴露了一个很隐蔽的坑：

```
19:07:11 第 1 位点「聘用候选人」
19:07:13 第 1 位 结果页没进展 → 快进(center) 第 1 次
   ...      一直点中央，点了 9 次
19:07:24 点「1 位 结果页没进展→快进(center)」快进 @(292,745)   ← 这行字不对劲
19:07:25 13s 内没走到出货卡（卡在 other），存 stuck 截图
```

最后那行 OCR 读到的文字，**是本脚本自己的日志**——说明 `mss` 抓屏拍到的是**面板窗口**，
不是游戏。面板盖在游戏上 → 脚本永远认不出出货卡 → 原地狂点 13 秒 → 判定失败跳过。
你看到的"在大厅发呆一段时间"就是这段。

`mss` 抓的是**屏幕上最前面**的东西，谁在最上层就拍谁。修法两条：

| 改动 | 说明 |
|---|---|
| `pc.focus_before_capture: true` | 每次抓屏前检查前台，不是游戏就先把它顶到最前（0.3s 限流，不折腾） |
| 面板「运行时最小化面板」（默认勾） | 开跑自动 `iconify()`，跑完 `deiconify()`，从根上不挡视线 |

另外把流程里的固定等待也换成了统一轮询间隔：

```yaml
ui:
  poll_delay: 0.2   # 「看一眼 → 决定下一步」之间的间隔（原来散落着 0.45/0.5/0.55）
```

领完一格 → 关卡 → 下一格开点，中间只剩状态判断（每次 ~15ms 抓帧 + 60ms 裁块 rec）。

## 速度：待机全部归零（2026-11-07）

以前每一步之间都固定 sleep 一下（`action_delay 1.2s` / `fast_delay 0.25s` / 每格 `0.4s`），
一轮四格光等待就吃掉十几秒。现在全部改成 **0**，进度靠「看一屏 → 决定下一步」的状态轮询：

```yaml
game:
  loop_interval_min: 0     # 跑完立刻下一轮（以前 5 分钟）
  slot_gap_sec: 0          # 每格之间不歇（以前硬编码 0.4s）
  idle_wait_sec: 0         # 空转也不等（真的零间隔）
  idle_stop_cycles: 3      # 连续 3 轮 0 产出 → 判定"没活儿了"，收工而不是空转
ui:
  action_delay: 0
  fast_delay: 0
  tap_time_delay: 0
  tag_tap_delay: 0
```

实测（同样 4 槽一轮）：

| | 改前 | 改后 |
|---|---|---|
| 面板 selftest 全流程 | 83s | **39s** |
| 面板启动到出结果（4 槽） | — | 38.9s（实测 exe `--selftest`） |
| 回归测试（23 项） | 225s | **99s** |

为什么敢把 sleep 设 0：真正决定节奏的是这些**状态判断**，不是睡眠——
`panel_state_fast()`（面板开没开）、`_wait_expedite_dialog()`（弹窗来没来）、
`claim_card_fast()` 的状态机、`advance_result()`（动画推没推进）。
固定 sleep 只是在它们之上白加时间。

> 唯一要注意的：如果哪天机器特别卡、或游戏掉帧严重，发现「点了没反应」，
> 把 `ui.fast_delay` 调回 `0.05`（50ms）就够，不用整套调回去。

## 模拟器排障（2026-11 实测：MuMu 15.x / Android 15 / AMD Vega8 / 游戏 2.7.91）

这一节是踩过的坑，按"症状 → 根因 → 修法"记，下次直接照抄。

| # | 症状 | 根因 | 修法 |
|---|------|------|------|
| 1 | `adb devices` 一会儿 `device` 一会儿 `offline`，`logcat` 卡在 `waiting for device` | 机器上装了两个版本的 adb：MuMu15 自带 `36.0.0`、i4Tools 自带 `29.0.4`，抢 5037 端口互相 kill server | 只用一个 adb：`config.yaml → adb.adb_path` 写死 MuMu 的 `D:/Program Files/Netease/MuMu/nx_main/adb.exe`，别的 adb.exe 别调 |
| 2 | 玩游戏 20~40 秒后**整个模拟器**直接退出（不是游戏崩，是模拟器没了） | 渲染后端是 Vulkan（`renderer_mode: vk`），宿主 `amdvlk64.dll` 崩：日志 `Renderer::error 901 / crashModule=amdvlk64.dll / Graphics Driver crash` | `renderer_mode: dx`（DirectX）。`MuMuManager.exe setting -v 0 -k renderer_mode -val dx` |
| 3 | 模拟器活着，但游戏起来 3 秒 SIGSEGV（`libunity.so` 空指针，`fault addr 0xfc`） | `force_discrete_graphics: true`，机器只有核显（Vega 8），硬走独显路径 | 设 `false` |
| 4 | 同上，游 3 秒 SIGSEGV | `renderer_strategy: auto`（或 `perf`）在该组合下同样触发空指针 | 设 `dis` |
| 5 | 启动游戏后又跳回桌面，前台变成 `cn.i4.mobile`（爱思助手） | 爱思助手随机自启抢前台 | `adb shell pm disable-user --user 0 cn.i4.mobile` |
| 6 | 游戏停在"正在释放神经递质(NNNMB/15077MB)"，看起来像卡死 | 2.7.91 首次安装要拉 ~15GB 资源（含语音包），本机约 3MB/s ≈ 1.5 小时 | 不是卡死，等；可以用 `adb shell cat /proc/net/dev` 看 wlan0 有没有在涨 |

### 出货读取（2026-11-03 定稿）

点完「聘用候选人」**不是**直接出货卡，中间还有一段黑箱装证件动画，整屏 OCR 只会拿到
`['SKIP','HUMAN','RESOURCE','DEPARTMENT']` —— 这就是 11-03 00:09「未识别出货干员」的根因。

### 加急后「开干员包」那一屏（2026-11-07 修）

加急券用掉之后，中间不只有黑箱动画，还会多出一屏**「开干员包」**——这一屏**整屏没有任何文字、也没有 SKIP**，
旧的状态机认不出它，只能干等到 9s 超时判失败，这一格的出货就白丢了（也就是「卡死」）。

现在 `core/ui.py` 里统一走 `advance_result()` 三级推进：

```
① 右上 SKIP 窄带 rec（60ms）      → 点 ui.skip_btn
② 整屏找「点击继续 / 继续 / 快进」 → 点文字中心（每 3 次才深扫一次，省 OCR）
③ 都没有（就是开包页）            → 点 ui.result_nudge（默认屏幕中央 0.5,0.5）= 快进
```

安全闸：动手前先 `screen_kind()`，**只要当前是列表 / 词条面板 / 大厅 / 基建就一下都不点**——
否则点中央正好落在某个公招格上，把后面几格全点乱（11-03 就是这么把游戏点回桌面的）。

接入点有四处，覆盖慢速和极速两条路径：

| 位置 | 作用 |
|---|---|
| `claim_card_fast()` | 状态机连续 2 拍对不上就推一次（最多 14 次），超时从 9s→13s |
| `read_result()` | SKIP 优先，然后推进；超时 45s→22s（该失败就早点失败） |
| `wait_result()` | 自然招募模式等结果时也顺手推 |
| `read_name_fast()` | 读不到名字时先推一次，再去做「是不是弹窗」的诊断 |

调参（`config.yaml`）：

```yaml
ui:
  result_nudge: {x: 0.500, y: 0.500}   # 快进兜底点，改成你屏幕上"点哪都行"的位置
  result_kw: ["点击继续", "点击屏幕", "继续", "快进", "跳过"]
```

真卡住时会自动存 `logs/shot_*_slotN_stuck.png`，照着那张图微调 `result_nudge` 就行。

### 出货卡之后的「干员介绍」也快进（2026-11-07 加）

抽到干员后不是只有一张卡：**新干员还会弹一屏「干员介绍」**（立绘 + 文字），
这一屏点一下就能跳过。旧逻辑只点卡面左下空白然后干等，遇到介绍页每格白花 2~4 秒。

现在 `skip_result_pages()` 按「看一屏 → 点一下」推进：

```
第 1 下：确认还在出货卡 → 点 ui.result_close（卡面左下空白，唯一能关卡的位置）
第 2 下起：介绍 / 演示页 → 点屏幕中央 = 快进
一旦回到公招列表立刻收手（多点的下一格会被误开词条面板）
```

| 配置 | 说明 |
|---|---|
| `ui.result_pages.max_taps` | 最多点几下（默认 4） |
| `ui.result_pages.timeout` | 最多花几秒（默认 3.5s） |

每次点击前都重新 `screen_kind()`：只要已经变成 列表/词条面板/大厅/基建 就**一下都不点**，
所以不会出现「介绍页关掉了又多戳两下把下一格点开」这种事故。

其他处理（`core/ui.py` 原有）：

1. `claim_candidates()` 点「聘用候选人」后立刻返回，不再一次性点 SKIP；
2. 整屏 OCR 漏字时，裁 `ui.result_name` 区域放大 2 倍再 OCR（艺术字名牌兜底）；
3. 干员名匹配只认中文文本，先把 `SKIP/HUMAN/123456` 这类噪声滤掉；
4. `close_result()` 用「公招列表页关键字」判定是否真的回到了列表，没回去就再点一次。

`tests/test_flow.py` 把这套状态链（`claim → anim(SKIP) → result`）固化成了回归测试，
`--dry-run` 的模拟器也照着真机改成三屏，改坏了会立刻红。

一条命令体检 + 自动写回推荐值：

```bash

python doctor.py --fix-emulator   # 写回推荐值（写完要重启模拟器：MuMuManager control -v 0 shutdown / launch）
```

# 电脑端（官方 PC 客户端）移植

模拟器版是「ADB 一句话 = 截图 / 点击」，PC 端没有 ADB，但**流程、决策、OCR、统计、推送一行都不用改** ——
因为整个项目只依赖 6 个设备动作。把这些动作换成 Win32 的等价物，其余全部复用。

## 1. 改造思路：加一层设备后端

```
core/runner.py
   └── create_backend(cfg)            ← 新增 core/device.py（工厂）
         ├── AdbClient   (模拟器/手机)  core/adb_client.py
         └── PcClient    (PC 客户端)    core/pc_client.py   ← 新增
                 ↓ 相同的鸭子接口
core/ui.py  ← 一行没改
```

两个后端暴露同一套方法，`core/ui.py` / `core/runner.py` 的流程代码完全不动：

| 设备动作 | ADB（原版） | PC 端（新增） |
|---|---|---|
| `screencap()` | `adb exec-out screencap`（~660ms） | `mss` 屏幕抓取 / `PrintWindow(PW_RENDERFULLCONTENT)`（**7~19ms**） |
| `tap(x,y)` | `adb shell input tap` | `SendInput` 绝对坐标，或 `PostMessage` 后台点击 |
| `tap_many(pts)` | 一条 shell 串多个 `input tap` | 一个循环连着发（按 `gap_ms` 间隔） |
| `swipe/long_press` | `input swipe` | 按下 → 逐帧移动 → 抬起 |
| `wm_size()` | `adb shell wm size` | `GetClientRect`（客户区，和截图同尺寸） |
| `current_package()` | `dumpsys window` 读前台包名 | 前台窗口 == 游戏窗口时返回 `game.package` |
| `start_app / kill_app` | `monkey` / `am force-stop` | `Popen(exe)` / `taskkill` |
| `alive()` | `adb get-state` | `SendMessageTimeoutW(WM_NULL)` 探活 |

坐标语义完全一致：**都是「客户区像素，左上角原点」**，所以 `ui.slots`、`ui.fast.*` 这些比例坐标原样可用。

```bash
# ① 把游戏窗口调成 1600x900（窗口化 / 无边框均可能，不要全屏独占）
#    —— ui.fast 那套极速裁块是按 1600x900 标的，这样能直接复用
```

## 4. 实测（2026-11-07，本机 1920x1080 / 官方 PC 客户端 1600x900 窗口）

| 项目 | 结果 |
|---|---|
| 窗口发现 | `「明日方舟」 class=UnityWndClass pid=36916` ✅ |
| 客户区读取 | 1600x900 / 1278x953 都读到过（随窗口变，已按 per-monitor v2 处理 DPI）✅ |
| 抓屏（mss） | 中位 **13ms**，最快 7ms（ADB 660ms，**快 50 倍**）✅ |
| 抓屏（PrintWindow） | 本机这台 **全黑**（返回 0.0 亮度）→ 所以默认走 mss ✅ |
| 坐标映射 + 注入（自检窗口） | `python pc_selftest.py` → **sendinput 4/4 命中，postmessage 0/4** ✅ |
| 游戏内点击 | 点到「公开招募」旁 15px 的「寻访历史记录」并真的打开了记录页 → **输入确实到达游戏** ✅ |
| 焦点抢占 | `SetForegroundWindow` 会被前台锁挡 → 已用「ALT + 0 位移鼠标 → AttachThreadInput → SwitchToThisWindow」三连解锁 ✅ |
| 权限 | 游戏进程 `OpenProcess(PROCESS_ALL_ACCESS)` → **error 5**：客户端是管理员启动的 ⚠ |
| 最小化还原 | 游戏最小化后，非管理员进程 `ShowWindow(SW_RESTORE)` **无效**（IsIconic 一直为 1）⚠ |

三条实测结论，决定了 PC 端的正确用法：

1. **必须以管理员身份运行**——不是为了「点得动」（sendinput 其实能到），而是为了**抢焦点 / 还原最小化窗口**；
   OpenProcess 被拒就说明游戏进程权限更高，这类跨进程窗口操作会被直接静默拒绝。
2. **必须 mss 抓屏**——本机 PrintWindow/GDI 对 D3D11 交换链回读是**全黑**，别指望它。
   代价是游戏必须在前台（被微信/终端盖住就会抓到别人的窗口）。
3. **坐标必须重标**——PC 版大厅布局与手机版不同：`entry_recruit` 实测文字中心 **(0.798, 0.714)**，
   原来模拟器那套 (0.789, 0.706) 差 15px 就点歪到「寻访历史记录」。已更新到 `config.yaml`，
   并给 `ensure_recruit_screen()` 加了「点歪到寻访页自动关掉重来」的自愈逻辑。

## 5. PC 端排障表（症状 → 根因 → 修法）

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | 截图全黑 | 抓的是窗口 DC，D3D 交换链不回读（本机实测就是这个） | 装 `mss` 用 `capture: "screen"`；别指望 `printwindow` |

## 6. 性能对照（同一套流程）

| 阶段 | 模拟器 + ADB | PC 端 |
|---|---|---|
| 抓一帧 | 660ms（raw） | **7~19ms** |
| 点一下 | 40~120ms（adb 往返） | **<5ms** |
| 一轮四槽 | ~25~30s（已优化到极限） | 理论 **3~5s**，瓶颈变成游戏动画等待 |
